# Дизайн score-based планировщика

## Цель

Заменить текущий планировщик `earliest-slot` на объяснимый рекомендательный алгоритм для производственных задач.

Планировщик должен при каждом пересчете заново собирать очередь из всего стека незавершенных задач, автоматически выбирать подходящее оборудование и операторов, по возможности соблюдать дедлайны и объяснять, почему была выбрана конкретная рекомендация.

## Текущий контекст

В проекте уже есть основные производственные сущности:

- `device_task`: производственная задача с длительностью, временем настройки, временем снятия изделия, дедлайном, приоритетом, выбранным устройством/оператором и плановым временем начала/завершения.
- `eqpmnt_characteristics`: характеристики оборудования и требований задачи внутри рабочего пространства.
- `devices_type`: типы оборудования, связанные с характеристикой.
- `device`: конкретное оборудование, связанное с типом устройства.
- `competencies_operator`: компетенции операторов по типам оборудования.
- `operator_device`: опциональная связь оператора с конкретным устройством.
- `user_task`: интервалы занятости оператора, перерывы и задачи смены.

Сейчас планировщик сортирует задачи по дедлайну и приоритету, а затем ищет ближайший слот для уже выбранных в задаче устройства и оператора. Этого недостаточно для целевого сценария рекомендаций: алгоритм не оценивает альтернативы, не выбирает лучшее оборудование, не объясняет решения и не пересобирает всю будущую очередь.

## Основное поведение

Когда добавляется новая задача или запускается пересчет плана, планировщик обрабатывает полный стек незавершенных задач, которые участвуют в рекомендациях.

Задачи делятся на две группы:

- Фиксированные задачи: уже завершены или выполняются прямо сейчас. Их интервалы нельзя двигать; они становятся занятыми интервалами.
- Подвижные задачи: еще не начались. Планировщик может их переносить, но только если каждая перенесенная задача остается в своем дедлайне.

Сначала планировщик пытается построить план, в котором новая задача помещается до своего дедлайна и ни одна подвижная задача не нарушает свой дедлайн. Если это невозможно, новая задача ставится в ближайший реальный слот и получает предупреждение о том, что выполнить ее в срок нельзя без нарушения ограничений.

## Входные данные задачи

Задачу нужно рассматривать как намерение выполнить работу, а не как ручную фиксацию устройства и оператора.

Основные поля задачи:

- Название.
- Дедлайн.
- Длительность, время настройки и время снятия изделия.
- Характеристика или требование к работе из справочников рабочего пространства.
- Опциональный ручной приоритет.
- Флаг участия в рекомендательной системе.

Примеры характеристик:

- Многоцветная печать.
- Обработка дерева.
- Требуется вытяжное оборудование.
- Материал или режим обработки.

Модель должна оставаться универсальной. Многоцветная печать - это один из возможных примеров характеристики, а не зашитое в алгоритм понятие.

## Построение кандидатов

Для каждой задачи планировщик строит комбинации ресурсов-кандидатов:

1. Определить требуемую характеристику задачи.
2. Найти типы оборудования, которые удовлетворяют этой характеристике.
3. Найти активные устройства этих типов, участвующие в рекомендациях.
4. Найти операторов, которые могут работать с выбранным типом устройства по компетенциям.
5. Опционально предпочесть операторов, закрепленных за конкретным устройством через `operator_device`.
6. Построить допустимые временные интервалы по доступности оборудования, доступности оператора, существующему плану и занятости из `user_task`.

Требования к оператору выводятся из оборудования и компетенций. Пользователь не задает требования к оператору напрямую в задаче.

## Модель оценки

Каждый кандидат - это связка:

```text
задача + устройство + оператор + интервал
```

Кандидат получает объяснимый балл, составленный из взвешенных критериев.

Начальные критерии:

- Срочность по дедлайну.
- Опциональный ручной приоритет.
- Соответствие оборудования характеристике.
- Эффективность или выгодность оборудования для характеристики.
- Более раннее возможное завершение.
- Штраф за просрочку.
- Штраф за перенос существующих задач.

Формула должна настраиваться через веса внутри рабочего пространства, а не быть одной жестко зашитой строкой.

Предлагаемое хранение:

- `planning_criteria`: справочник поддерживаемых критериев.
- `planning_weights`: веса критериев для рабочего пространства.
- `device_characteristic_score`: оценка или предпочтительность конкретного устройства для конкретной характеристики.

Так один принтер может быть предпочтительнее для многоцветных задач, но более ранний слот сможет победить, если дедлайн под угрозой.

## Правила перепланирования

Планировщик может переносить подвижные задачи только если выполняются все условия:

- Задача еще не началась.
- Задача не завершена.
- Новый интервал не выходит за дедлайн этой задачи.
- Перенос не конфликтует с фиксированными интервалами оборудования или оператора.

Планировщик не должен выполнять новую задачу за счет того, что другая задача выйдет за свой дедлайн.

Если план без просрочек для новой задачи невозможен, планировщик переходит в режим реального плана:

- Сохраняет фиксированные ограничения.
- Находит ближайший допустимый слот выполнения.
- Сохраняет предупреждение о том, что задача не укладывается в дедлайн.
- Возвращает или сохраняет ближайшее реалистичное время завершения.

## Выход рекомендации

Планировщик должен сохранять и возвращать больше данных, чем только `plan_start` и `plan_end`.

Рекомендуемый выход:

- Плановое начало и завершение.
- Выбранное устройство.
- Выбранный оператор, если он требуется.
- Итоговый балл.
- Код и текст предупреждения, если оно есть.
- Человеко-понятное объяснение.
- Альтернативные кандидаты, когда это полезно.
- Список задач, которые были перенесены.

Предлагаемое хранение:

- `planning_run`: один запуск пересчета, рабочее пространство, время запуска, статус.
- `planning_recommendation`: результат по задаче и кандидату, включая флаг выбранного варианта, балл, предупреждение, объяснение, устройство, оператора, начало и завершение.

Существующие поля `device_task.plan_start`, `device_task.plan_end`, `device_task.device` и `device_task.operator` можно продолжать использовать для хранения примененного выбранного плана и совместимости с текущим интерфейсом.

## Контур алгоритма

1. Загрузить задачи рабочего пространства, которые не завершены и включены в рекомендации.
2. Разделить задачи на фиксированные и подвижные по текущему времени, отметке завершения и плановым интервалам.
3. Загрузить устройства, типы устройств, характеристики, операторов, компетенции, закрепления операторов за устройствами, пользовательские задачи, веса планирования и оценки устройств по характеристикам.
4. Создать календари занятости из фиксированных задач и `user_task`.
5. Построить комбинации ресурсов-кандидатов для каждой подвижной задачи.
6. Попробовать строгое планирование:
   - Поставить задачи в очередь по риску дедлайна, ручному приоритету и взвешенному баллу задачи.
   - Искать допустимые слоты до дедлайна каждой задачи.
   - Разрешать перенос будущих задач только если их дедлайны остаются соблюдены.
7. Если строгое планирование не может поставить новую задачу в срок, запустить fallback-планирование:
   - Найти ближайший реалистичный слот, даже если он завершается после дедлайна новой задачи.
   - Пометить рекомендацию предупреждением о дедлайне.
8. Оценить выбранные и альтернативные кандидаты.
9. Сохранить выбранный план и объяснение рекомендации.
10. Вернуть счетчики, предупреждения, выбранные планы, альтернативы и список незапланированных задач, если требования к ресурсам вообще невозможно удовлетворить.

## Влияние на API

Нужно расширить ответ `POST /api/plans/recompute`: вместо простого количества обновленных задач возвращать объяснимый результат.

Примерная форма ответа:

```json
{
  "run_id": 42,
  "updated": 5,
  "warnings": [
    {
      "task_id": 12,
      "code": "deadline_missed",
      "message": "Невозможно выполнить до дедлайна без нарушения сроков других задач."
    }
  ],
  "recommendations": [
    {
      "task_id": 12,
      "device_id": 3,
      "operator_id": 7,
      "plan_start": "2026-05-23T09:00:00Z",
      "plan_end": "2026-05-23T14:30:00Z",
      "score": 87.5,
      "selected": true,
      "explanation": "Выбран ближайший реальный слот; дедлайн недостижим без просрочки других задач."
    }
  ],
  "unscheduled_ids": []
}
```

## Влияние на UI

Интерфейс должен показывать работу алгоритма, а не скрывать ее:

- Бейдж предупреждения на задачах, которые не укладываются в дедлайн.
- Панель объяснения для выбранной рекомендации.
- Редактор критериев и весов в справочниках или настройках планирования.
- Управление оценками "устройство - характеристика" рядом с оборудованием или характеристиками.
- Альтернативные рекомендации, если более подходящее устройство проиграло более раннему слоту.

## Стратегия тестирования

Перед изменением поведения планировщика нужно добавить тесты на уровне service-слоя:

- Фиксированная выполняемая задача никогда не переносится.
- Подвижная задача может переноситься только если ее дедлайн остается соблюденным.
- Новая задача ставится до дедлайна, если существует допустимое перепланирование.
- Новая задача получает предупреждение и ближайший реалистичный слот, если допустимого перепланирования нет.
- Оператор выводится из компетенции по выбранному типу оборудования.
- Устройство с более высокой оценкой характеристики выигрывает при равных дедлайнах.
- Более ранний слот выигрывает у предпочтительного устройства, если иначе дедлайн был бы сорван.
- Отсутствие совместимого оборудования дает незапланированную рекомендацию.

## Не входит в цель

- Полная оптимизация всех возможных перестановок для очень больших производственных очередей.
- Жесткое зашивание 3D-печатных полей вроде многоцветности в алгоритм.
- Полная замена всего интерфейса до стабилизации алгоритма и модели данных.
